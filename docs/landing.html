Why teams use these emulators

Spec-faithful by construction. The only sources of truth are official artifacts — VDA 5050's published JSON schemas (vendored with pinned hashes, re-checked weekly), MiR's own API documents, Omron's public reference manual. Where a spec and its prose disagree, the wire format wins, and the divergence is documented.

Externally validated. Passing your own tests proves consistency, not correctness — so these emulators are run against independent implementations: NVIDIA Isaac Mission Dispatch completed missions against the VDA 5050 robot and broker; the InOrbit/OTTO connector executed orders from the master-control side. Transcripts ship in the repo.

Built to be broken. Fault injection is a first-class surface: emergency stops, localization loss, battery collapse, connection drops, forced action failures — so your integration's worst day happens on an emulator, not on a warehouse floor.

Sixty seconds to a running robot

# VDA 5050: embedded broker on :1883 + one emulated robot
uvx vda5050-emulator

# your MiR robot as a VDA 5050 robot (any master control can drive it)
uvx mir-vda5050-adapter --mir-url http://<robot-ip> --broker <mqtt-host>

# an Omron LD/HD that answers on telnet
uvx arcl-emulator
